# Quran Decipherment Project — Design Spec

**Date:** 2026-04-12
**Status:** Draft, in-flight (user authorized starting work in parallel with finalizing the spec)
**Orchestrator:** Claude (Opus 4.6, 1M context)

## 1. Mission

Systematically analyze the Quranic Arabic text in three sequential phases:

- **Phase A — Replication / Audit.** Catalog every published "mathematical miracle" or numerical-pattern claim about the Quran. Reproduce each one against the raw text we have downloaded, using *explicit and disclosed* counting rules. Mark each as `verified`, `partially verified`, `failed`, `inconclusive`, or `requires-extra-data`. The output is an honest audit table — most public claims have never been replicated this carefully.
- **Phase B — Hypothesis hunting.** With analytic tools and counting infrastructure built in Phase A, run open searches for novel statistical structure: gematric distributions, surah-length sequences, palindromic ayah positions, prime/composite indices, cross-surah symmetries, n-gram signatures, positional analysis of the 14 huroof muqatta'at surahs, etc. Every novel finding must be tested against null models before being called significant.
- **Phase C — Structural cartography.** Less about counts, more about *wording schema*: chiastic / ring composition, intra-surah symmetry, root-distribution maps, anchoring words, cross-surah linkages.

## 2. Non-goals

- Not arguing for or against the divine origin of the Quran.
- Not refuting religious claims; we report what survives replication.
- Not cherry-picking counting conventions to fit a desired result.
- Not inventing new claims without testing them against null models.
- Not generating unverifiable "discoveries" to satisfy the desire for novelty.

## 4. Methodology — the part nobody does

The single most important insight in this space: **a numerical claim about the Quran is meaningless without disclosing its counting rules.** Almost every famous "miracle" claim that fails replication fails because the original claimant used a non-standard rule and didn't disclose it; conversely, claims that look like cherry-picking sometimes survive scrutiny once the rule is made explicit.

Every claim — whether replicated from literature or generated by us — must carry a `rules` tuple:

```yaml
rules:
  orthography: full-tashkeel | min-tashkeel | no-tashkeel | uthmani-rasm
  word_definition: orthographic-token | lemma | with-clitics-split | dictionary-headword
  letter_definition: graphemes | phonemes | shadda-doubled | hamza-collapsed | ...
  basmala_policy: counted-in-surah | counted-only-in-surah-1 | always-separator
  verse_numbering: hafs-kufan | warsh-madanian | ...
  abjad_table: standard-mashriqi | maghribi | ...   # only relevant for gematria
  null_model: ...                                    # only for novel findings (Phase B+)
```

Without this tuple, a number is just a number. With it, claims become *replicable propositions*.

See `docs/methodology.md` for the full specification.

## 6. Agent topology

The user explicitly requested a **team** of agents that can communicate, not just isolated subagents.

Claude Code's actual primitive: named subagents addressable via `SendMessage`. Real peer-to-peer messaging requires the orchestrator (this main session) to act as message bus — there is no independent message channel between sibling agents. We will:

1. Spawn long-running named agents for streams of work that produce shared dependencies (`lit-catalog`, `morph-data`, `stats-rigor`).
2. Spawn short-lived parallel workers for embarrassingly-parallel claim verification (one per claim cluster in Phase A2).
3. Use `SendMessage` to relay findings between named agents through the orchestrator.
4. Maintain `journal/` with one log file per agent run for audit trail.

**Initial roster (Phase A1 — research and data acquisition):**

| Agent | Type | Mode | Purpose |
|---|---|---|---|
| `lit-catalog` | general-purpose | bg | Exhaustive literature review of every published Quranic-numerology claim |
| `morph-data` | general-purpose | bg | Acquire Quranic Arabic Corpus + Tanzil + companion datasets |
| `stats-rigor` | general-purpose | bg | Best-practice null-model methodology, lessons from Bible-Code debunking literature (McKay et al. 1999) |
| `text-shape` | general-purpose | fg | Investigate the word-count discrepancy across the three flat tashkeel variants |

Phase A2 will spawn one verification worker per claim cluster, in parallel.

## 8. Honest limits

- Many famous claims will fail replication. We report failures with the same prominence as successes.
- "Revolutionary discovery" requires extraordinary evidence: statistical validation against multiple null models AND prior-art search confirming nobody else has reported it.
- Some claims require manuscript-level orthographic data we may not be able to acquire. Those go to `inconclusive — deferred`.
- Confirmation bias is the enemy. The `stats-rigor` agent and the red-team review at the end of each phase exist specifically to fight it.

## 9. Process

We work in phases A → B → C, but Phase A1 (literature + data acquisition + tooling foundation) is parallelizable across many agents and runs immediately. Phase A2 (per-claim replication) blocks on A1 outputs. Phase B blocks on A complete. Phase C can begin in parallel with B once tooling stabilizes.
